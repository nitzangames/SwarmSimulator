Data-oriented design.
In your browser.

JavaScript simulates the flock on the CPU. Three.js draws it on the GPU. Typed arrays keep the simulation data contiguous, while a spatial grid keeps the work predictable as the population grows.

Typed arrays→Spatial grid→Steering→Three.js
01

Store fields in arrays. An agent is an index.

Positions and velocities use separate Float32Array buffers: a Structure of Arrays layout. Slot agentIndex identifies the same agent in every buffer. We allocate the full pool once and track its live population with agentCount.

SIMPLIFIED ALLOCATION · gameData.js ↗ 
const capacity = 300_000;

const gameData = {
  positionX: new Float32Array(capacity),
  positionY: new Float32Array(capacity),
  velocityX: new Float32Array(capacity),
  velocityY: new Float32Array(capacity),
  agentCount: 12_000,
};

No individual agent objects, update methods, or per-frame buffer allocations. The complete simulation pool, including grid scratch space, uses about 8.1 MiB.

02

Separate the data from the logic.

Logic functions receive data, transform it, and write results back. They know nothing about Three.js or the DOM. That makes the same simulation runnable in a browser, a Node test, or a CPU benchmark.

POSITION UPDATE · logic.js ↗ 
function integratePositions(gameData, balance, stepSeconds) {
  for (let agentIndex = 0; agentIndex < gameData.agentCount; agentIndex++) {
    const nextX = gameData.positionX[agentIndex]
      + gameData.velocityX[agentIndex] * stepSeconds;
    const nextY = gameData.positionY[agentIndex]
      + gameData.velocityY[agentIndex] * stepSeconds;

    // Wrap positions at the world boundaries.
    gameData.positionX[agentIndex] = (nextX + balance.width) % balance.width;
    gameData.positionY[agentIndex] = (nextY + balance.height) % balance.height;
  }
}

The project follows five roles: Balance holds constants, GameData owns mutable arrays, Logic transforms them, Board handles rendering and input, and Game drives one animation loop.

03

Do nearby work once. Share the result.

A counting-sort grid groups agent indices into contiguous cell ranges. We aggregate position and velocity across nine neighboring cells once per cell, then reuse those averages for alignment and cohesion. Separation checks up to two occupants in each of the four nearest cells: at most eight candidates per agent.

This keeps work O(N + grid cells). It is an approximate boids model: separation uses a rotating sample, not every nearby agent. A gentle global flow shapes each preset. Positions update only after every agent has read the previous frame.

04

Render the whole flock in one Three.js draw call.

A single InstancedBufferGeometry repeats a two-triangle shape. Its instance attributes reference the simulation arrays directly, and the vertex shader rotates each shape to face its velocity. No per-agent mesh or transformation matrix is needed.

SIMPLIFIED RENDERING · board.js ↗ 
const geometry = new THREE.InstancedBufferGeometry();
const positionAttribute = new THREE.InstancedBufferAttribute(
  gameData.positionX,
  1,
).setUsage(THREE.DynamicDrawUsage);

geometry.setAttribute("agentPositionX", positionAttribute);
geometry.instanceCount = gameData.agentCount;

// The full renderer also supplies Y, both velocities, and shape vertices.
// Upload the live array prefix, then draw the one instanced mesh.
renderer.render(scene, camera);

Typed arrays are uploaded to GPU buffers; this is not zero-copy CPU/GPU shared memory. Reusing the simulation arrays avoids an extra CPU packing buffer. After the initial upload, only the live prefixes are sent each frame.

05

Measure the device. Adjust the population.

Auto-scale watches actual animation-frame intervals and CPU work in one-second windows. It warms up, grows after healthy windows, and reduces the flock when the budget is exceeded. Delayed probes test whether more capacity becomes available.

60 fps is a target. Display refresh rate, browser scheduling, hardware, battery settings, and thermal throttling affect the sustainable population. The 300,000-agent pool is a capacity limit. The readouts measure frame intervals and CPU simulation time; they are not GPU timestamps.
